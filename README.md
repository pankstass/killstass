# KILLSTASS 1.15.0

Локальный журнал игр Warhammer 40,000: Kill Team: общие матчи с друзьями, счёт VP/CP, снаряжение и ploys с телефона, гостевые записи и локальные игроки клуба, SQL-статистика и рейтинг Эло, справочник правил с подсказками терминов и карты киллзон с готовыми раскладками террейна. Основные правила Kill Team (v1.12, с v1.13 — только действующий текст) входят в поставку; справочник команд и схемы ростеров (v1.7–1.8) и общие правила оружия (v1.11) администратор сервера загружает сам из общественных репозиториев.

## Что нового в 1.15.0

- Faction Rules: команды разделены на Imperium, Chaos и Xenos, добавлены локальные эмблемы; три отсутствующие у источника отмечены заменителями.
- Tac Ops сгруппированы по архетипам с цветовой индикацией.
- В «Record a match» можно записать результат с зарегистрированным игроком по публичному ID; соперник должен подтвердить результат. Миграция `017_v115.sql`. Подробности — `docs/26-v1.15.md`.

## Исправление 1.14.1

Исправлена вероятная причина белого экрана при одновременной загрузке модулей: увеличен лимит соединений, устранено длительное кэширование ошибок, ограничен параллелизм установки service worker. При ошибке запуска доступен экран восстановления. См. `docs/25-v1.14.1.md`.

## Что нового в 1.13.0

- **«Сдаться»** в меню табло: матч заканчивается сразу, на любом поворотном моменте, со счётом **10:0** в пользу соперника; в матче с другом соперник только подтверждает результат, на одном устройстве сдаться может любой из игроков.
- **Локальные игроки** — участники клуба без аккаунта: общий список для матчей на одном устройстве и быстрых записей (подсказки в поле соперника, флажок «Локальный игрок»), **рейтинг Эло «Весь клуб»** вместе с ними (переключатель «Друзья | Весь клуб» в статистике), администратор удаляет записи в `#admin`.
- **Число оперативников** при подготовке матча — из прикреплённого ростера, иначе по составу выбранной команды; вручную — только если ни того, ни другого нет, или по кнопке «Изменить».
- **Калькулятор атаки**: свойства оружия — кнопками (Accurate, Balanced, Ceaseless, Relentless, Lethal, Rending, Punishing, Severe, Devastating, Piercing, Piercing Crits, Saturate) со значениями; **универсальные гранаты** — осколочная и крак-граната.
- **Подсказки** при наведении (фокусе, касании) на игровые термины (Control range, Obscured, Valid target…), типы местности, универсальные действия и свойства оружия — официальные определения из основных правил; в датакартах, правилах фракций, кратком справочнике и основных правилах. Импорт данных команд не менялся.
- **Основные правила** — только действующий текст: без пометок «обновлено»/«добавлено» и без страниц PDF; сверено с официальным Core Rules: Update Log (warhammer-community.com, 28.10.2026).

## Документация для разработчиков и текущая поставка

**v1.1.1 — полный архив**, не patch: для первой установки не требуется v1.0. Включены исправления tmpfs, non-root запуска Caddy, TLS по IP и role-level JIT; данные матчей/каталог и миграции 001–004 не менялись. `.env` и рабочие volumes не поставляются и не должны заменяться при обновлении.

- [Руководство разработчика и оператора](docs/10-developer-handbook.md): архитектура, инварианты, исходники, диагностика, установка, обновление, backup/restore.
- [Журнал реального развёртывания](docs/11-deployment-changelog.md): что наблюдалось, что исправлено и что не подтверждено.
- [Инструкция обновления](UPDATE-INFO.md), [фактические проверки и ограничения](docs/07-verification.md).

Если ручные исправления уже применены и сайт работает, переустановка не обязательна. Для обновления сверить локальные изменения, сохранить `.env`/volumes, выполнить штатный `scripts/update.sh` после backup; полный порядок — руководство §7.2. Новые SQL-миграции для v1.1.1 не добавлены: JIT выставляет мигратор после создания роли.

### 7.4 Межсетевой экран: обнаружить, а не заменить

До запуска контейнеров проверьте активные службы и правила как root:

```sh
su -
systemctl is-active nftables iptables firewalld || true
systemctl list-unit-files | grep -E 'nft|iptables|firewalld'
command -v nft && nft list ruleset
command -v iptables && iptables --version
command -v iptables && iptables -S
command -v iptables && iptables -S DOCKER-USER
systemctl cat docker
```

Состояние systemd-службы само по себе не доказывает отсутствие правил: Docker/fail2ban добавляют их независимо. `iptables --version` с `nf_tables` — совместимость iptables-nft, **не** обязательно native nft backend Docker. Если цепочка DOCKER-USER существует — используем её; при native nft у Docker её нет.

Проект содержит `scripts/firewall.sh`:

- при iptables создаёт только собственную KILLSTASS-LAN и jump из DOCKER-USER;
- фильтрует **исходный адрес/порт conntrack до DNAT**, 192.168.1.250:80/443, направление ORIGINAL;
- при native nft создаёт собственную таблицу inet killstass с forward/input guard;
- запрещает этим портам источники вне сетей `KS_ALLOW_NETS` из `.env` (по умолчанию 192.168.1.0/24; `scripts/tailscale.sh` добавляет 100.64.0.0/10); остальные правила/порты не затрагивает;
- не делает `flush ruleset`, не отключает Docker iptables, не меняет policy FORWARD и не трогает fail2ban/SSH.

```sh
/opt/killstass/scripts/firewall.sh
install -m 644 /opt/killstass/systemd/killstass-firewall.service /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now killstass-firewall.service
```

**Это защитный ограничитель, а не обход существующего default DROP.** Если ваш управляемый firewall уже блокирует LAN→Docker FORWARD, нужно добавить узкое разрешение в *его* цепочку перед запрещающим правилом. Нельзя автоматически угадать имя цепочки и безопасное место вставки. Для iptables типовой пример (только после проверки интерфейса/правил):

```sh
# В DOCKER-USER выше вашего generic DROP, если именно он мешает LAN:
iptables -I DOCKER-USER 1 -i wlp2s0 -s 192.168.1.0/24 -p tcp \
 -m conntrack --ctdir ORIGINAL --ctorigdst 192.168.1.250 --ctorigdstport 443 -j RETURN
iptables -I DOCKER-USER 1 -i wlp2s0 -s 192.168.1.0/24 -p tcp \
 -m conntrack --ctdir ORIGINAL --ctorigdst 192.168.1.250 --ctorigdstport 80 -j RETURN
```

RETURN продолжает штатную обработку Docker; это не глобальный ACCEPT. При собственном DROP *раньше jump DOCKER-USER* разместите эквивалентное разрешение перед ним в своей управляемой конфигурации. Для nft интегрируйте в существующую forward-цепочку, подставив реальные family/table/chain из `nft list ruleset`:

```sh
# Пример выражения для существующей forward-цепочки, НЕ команда с выдуманным именем:
# iifname "wlp2s0" ip saddr 192.168.1.0/24 meta l4proto tcp \
# ct original ip daddr 192.168.1.250 ct original proto-dst {80,443} accept
```

В nft отдельное ACCEPT не отменяет DROP в другой base chain: используйте конфигурацию активного firewall, а не выключайте его. Сначала сохраните правила (`iptables-save`/`nft list ruleset` в защищённый файл). После reload firewall и рестарта Docker повторно проверьте guard, при необходимости `systemctl restart killstass-firewall`. Перезапуск firewall с очисткой всего ruleset требует восстановить и Docker-правила — не делайте этого во время матча.

Второй независимый барьер — `remote_ip` у Caddy с теми же сетями `KS_ALLOW_NETS`. API/БД вообще не публикуют порты, IPv6/UDP443 не публикуются. Не монтируйте Docker socket в приложение.

### 7.5 Первый запуск и доверие к HTTPS

```sh

# Только защищённая локальная диагностика; -k не использовать постоянно на клиентах:
curl -k https://192.168.1.250/api/health

Ожидается `{"status":"ok"}`. Первый старт создаёт БД, применяет миграции 001–004 и проверенные справочники Approved Ops 2025; последующие не пересоздают данные. Сумма mem_limit — 1152 МиБ, то есть ниже 1.5 ГиБ. Сборка образов не ограничена runtime mem_limit; выполняйте её без параллельных тяжёлых задач. ```sh

openssl x509 -in killstass-root.crt -noout -subject -fingerprint -sha256
```

Передайте root.crt доверенным способом на устройства, сверив SHA256 fingerprint. **Не копируйте root.key, intermediate.key или том Caddy.** На Windows импортируйте сертификат в «Доверенные корневые центры сертификации» текущего пользователя; Firefox при отдельном хранилище требует импорт CA; Android — пользовательский CA через настройки безопасности; iOS — профиль, затем явно включить полное доверие в настройках сертификатов. Названия меню зависят от версии ОС. Публичный CA не нужен.

Откройте `https://192.168.1.250`. После доверия браузер должен показывать защищённое соединение. HTTP перенаправляется на HTTPS. Регистрация первого пользователя обычная, предустановленного администратора/пароля нет. Зарегистрируйте второго игрока на другом устройстве, обменяйтесь ID → заявка → принять → вызов → принять → подготовка → сохранить → начать. Для нового матча оба игрока должны сохранить свои Tac Op и число оперативников для Kill Op (5–14). Основную цель предварительно выбирают в настройке и тайно фиксируют как гамбит первого поворота; после четырёх поворотов отправляют результат на подтверждение.

### 7.6 Домен, Let's Encrypt, Tailscale и push (необязательно)

С v1.10 это делают скрипты (как root в `/opt/killstass`); они правят `.env` атомарно и перезапускают нужные сервисы. Подробно — [docs/20-v1.10.md](docs/20-v1.10.md).

```sh
./scripts/domain.sh set killstass.su     # KS_DOMAIN, APP_ORIGIN=https://192.168.1.250,https://killstass.su
./scripts/cert.sh issue                  # Let's Encrypt через DNS-01: ACME_EMAIL, ACME_DNS_PROVIDER в .env, ключи API в local/acme.env (0600)
cp systemd/killstass-cert.* /etc/systemd/system/ && systemctl daemon-reload && systemctl enable --now killstass-cert.timer
./scripts/tailscale.sh enable tskey-auth-…   # доступ извне без проброса портов; подтвердите маршрут 192.168.1.250/32 в консоли Tailscale
./scripts/push.sh enable mailto:you@example.org
```

Домен должен разрешаться в `192.168.1.250`: A-запись у регистратора (частный адрес, снаружи сайт недоступен) или запись в DNS роутера; если роутер отбрасывает ответы DNS с частными адресами (защита от DNS rebinding), добавьте для домена исключение или локальную запись. Чисто локальное имя (`killstass.lan` в hosts или DNS роутера) задаётся тем же `domain.sh set killstass.lan`, сертификат тогда остаётся от внутреннего CA Caddy. `APP_ORIGIN` — список origin через запятую; сайт продолжает работать и по IP, но cookie привязана к хосту — входите отдельно по каждому адресу. Сервис-воркер (офлайн-табло) и push телефоны включают только на доверенном HTTPS, то есть на домене с сертификатом Let's Encrypt.

### 7.7 Если Docker Hub недоступен

Нельзя без проверки подставлять `registry.altlinux.org/postgres:16-alpine`: наличие такого образа/совместимость не гарантированы. `registry.altlinux.org` можно использовать для доступных там **проверенных** образов ALT, но это не прозрачная замена официальных Python/PostgreSQL/Caddy Dockerfile.

### 7.8 Обновление, эксплуатация и HDD

Не удаляйте volumes. `docker compose down -v` **удаляет БД и частный CA**. Обычная остановка `docker compose stop`, запуск `docker compose up -d`. Посмотреть нагрузку: `docker stats --no-stream`; место: `df -h`, `docker system df`. Не запускайте регулярный `docker system prune --volumes`.

Бэкап перед обновлением обязателен — `update.sh` делает его сам. С v1.10 выпуск ставится прямо из ZIP, как root (из-за каталога резервных копий):

```sh
su -
cd /opt/killstass
./scripts/update.sh /root/killstass-v1.11.0.zip   # рядом — killstass-v1.11.0.zip.sha256 (или --sha256 HEX)
./scripts/update.sh --rollback                    # вернуть предыдущий выпуск: код, .env, образы :prev
exit
```

В режиме ZIP скрипт до каких-либо изменений проверяет SHA-256 архива, распаковывает его во временный каталог и сверяет `SHA256SUMS`: лишние, подменённые файлы, символические ссылки, пути с `..` и файлы `.env`, `local/`, `backups/` отвергаются, версия должна быть новее установленной (иначе только `--force`). Затем сохраняет дамп, код и копию `.env` в `/var/backups/killstass` (5 последних выпусков) и образы как `:prev`, раскладывает новые файлы (`.env`, `local/` и `backups/` не трогаются) и выполняет обычный порядок ниже. Если любой следующий шаг не прошёл — автоматический откат кода, `.env` и образов с проверкой health; БД не откатывается (миграции только добавляют), команда `restore.sh` с дампом печатается. Без аргумента `update.sh` работает, как раньше, — с файлами, уже разложенными вручную с сохранением `.env`.

Скрипт делает дамп, собирает образы, проверяет новый `Caddyfile` и compose (`scripts/smoke.sh --pre`, старая версия ещё работает), останавливает API/proxy, пересоздаёт db без удаления volume, применяет новые миграции, поднимает стек и проверяет его (`scripts/smoke.sh --post`: health, версия, миграции, статика через Caddy). Если миграция не прошла при обновлении без ZIP, API остаётся остановленным; не обходите ошибку запуском старого бинарника против новой схемы. Верните предыдущую версию проекта/образов (`update.sh --rollback`, если прошлое обновление было из ZIP) и восстановите совместимый дамп. Ветка PostgreSQL остаётся 16: переход на 17/18 — отдельная процедура pg_upgrade или dump/restore, не замена тега с существующим volume.

Теги базовых образов зафиксированы по ветке/версии, не по digest; для воспроизводимой поставки после собственной проверки закрепите digest в `.env` и храните образный архив. Перед production проверяйте обновления безопасности зависимостей/образов, прогоняя тесты. Не обещаем, что старый точный tag всегда содержит последние исправления.

HDD-настройки: shared_buffers=128MB, work_mem=2MB, max_connections=24, checkpoint_timeout=15min, max_wal_size=256MB (мягкая цель, не жёсткий лимит места), WAL/checksums/fsync/synchronous_commit не отключены. Autovacuum включён. Логи ограничены 2×5MiB на сервис, access-log API выключен; состояние счётчиков не пишется в лог каждую секунду. Нет Redis, брокера, Celery или периодического пересчёта статистики. Свободное место под WAL/дампы и резерв на временные сборки обязательно.

Пароли в .env используются только при первичной инициализации ролей: изменение строки **не меняет пароль существующей БД**. Для ротации остановите api, измените пароль роли через psql `\password killstass_app` в интерактивном сеансе владельца, затем синхронно `.env` и `docker compose up -d --force-recreate api`; пароль не включайте в командную строку/историю. Для роли владельца также обновите `.env`. Не стирайте том ради ротации.

### 7.9 Резервные копии и systemd timer

`pg_dump -Fc -Z3`, атомарный rename, проверка оглавления, flock от параллельного запуска; по умолчанию последние 14 копий. Файлы 0600, каталог root. Это **не** непрерывное восстановление WAL и не резервирование всего хоста.

```sh
su -
cd /opt/killstass
install -d -m 700 /var/backups/killstass
install -m 644 systemd/killstass-backup.service systemd/killstass-backup.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now killstass-backup.timer
systemctl start killstass-backup.service
systemctl list-timers killstass-backup.timer
journalctl -u killstass-backup.service -n 30 --no-pager
ls -lh /var/backups/killstass
```

Расписание 04:30 Europe/Moscow с разбросом до 10 минут; Persistent выполнит пропущенный запуск после загрузки. Измените KEEP_BACKUPS через `systemctl edit killstass-backup.service`, добавив `[Service] Environment=KEEP_BACKUPS=30`; затем daemon-reload.

Копирование на основной ПК: здесь **ПК забирает копию по уже существующему SSH сервера, порт 2026**, серверу не нужны ключи/пароль ПК. На сервере как root подготовьте последний файл:

```sh
install -d -m 700 -o sslaveh -g sslaveh /home/sslaveh/killstass-transfer
latest=$(ls -1 /var/backups/killstass/killstass-*.dump | sort | tail -n 1)
install -m 600 -o sslaveh -g sslaveh "$latest" /home/sslaveh/killstass-transfer/
# Для переноса сразу с версией сохраните отдельно архив текущего кода без .env.
exit
```

На ПК:

```sh
scp -P 2026 'sslaveh@192.168.1.250:/home/sslaveh/killstass-transfer/killstass-*.dump' ./backups/
```

Создайте `./backups/` заранее; защитите диск ПК/каталог. После проверки переноса удалите staging-файлы на сервере (не рабочие резервные копии). Для автоматического off-host pull настройте планировщик **ПК** и выделенное ключевое соединение; не пересылайте приватные ключи в контейнеры.

`.env` и приватный CA не входят в pg_dump. `.env` храните отдельно в зашифрованном хранилище; при утрате можно создать новые роли/пароли при восстановлении. Если хотите сохранить доверие существующих клиентов после потери сервера, нужен отдельный **зашифрованный** backup caddy_data; иначе выпустите новый CA и переустановите публичный root.crt на клиентах. Дампы содержат персональные игровые данные и сессии: не публикуйте их. При восстановлении скрипт очищает все сессии. Анонимизация аккаунта не стирает его из уже существующих копий до окончания retention.

### 7.10 Восстановление

Проверяйте восстановление регулярно, в отдельной установке/томе. Для production выберите **версию проекта, совместимую с дампом**; образ с будущими таблицами нельзя бездумно накатывать поверх старого дампа. Свежую базу сначала инициализируйте той же версией схемы. Сначала сохраните текущую копию.

```sh
su -
cd /opt/killstass
./scripts/backup.sh
./scripts/restore.sh /var/backups/killstass/killstass-YYYYMMDDTHHMMSSZ.dump --yes
docker compose ps
# Дальше проверить с доверенного LAN-клиента: вход, журнал, пару итоговых матчей.
exit
```

`restore.sh` останавливает API/proxy, проверяет архив, восстанавливает в одной транзакции, возвращает права app-ролям мигратором, удаляет все сессии и запускает API/proxy. При любой ошибке оставляет их остановленными: проверьте журнал, не редактируйте дамп вручную. Выберите настоящее имя файла, а не шаблон YYYY. Если владелец app-роли в старом кластере уже существует с иным паролем, синхронизируйте его с `.env` через `\password`, мигратор существующий пароль намеренно не перезаписывает.

### 7.11 Тесты

Сервер и backend-разработка не требуют Node.js; он нужен только для линтера и браузерных e2e-тестов (Node 22+, `npm ci && npm run lint && npm run e2e`, или всё в Docker — `./scripts/e2e-docker.sh`; см. [docs/19-v1.9.md](docs/19-v1.9.md)). Python 3.12 рекомендуется; тестовая проверка также проведена на Python 3.13. Установка тестовых зависимостей на рабочей машине:

```sh
python3 -m venv .venv
. .venv/bin/activate
pip install -r api/requirements.txt pytest==8.4.1 httpx==0.28.1
./scripts/test.sh
```

Интеграционные тесты **удаляют все пользовательские записи в выделенной test-базе**. Никогда не подставляйте production URL. Создайте отдельную PostgreSQL 16 UTF8 БД с именем, содержащим `test`, примените `db/migrate.sh` с доступным `/opt/killstass/{migrations,seed.json}`, где seed.json для неизменённой 002 — копия db/legacy-seed.json (в Docker это уже есть). Введите тестовые DSN в переменные окружения, не коммитьте их:

```sh
# TEST_DATABASE_URL — владелец тестовой БД; DATABASE_URL — killstass_app той же БД.
# Устанавливаются локально; пароли не вставляйте в общедоступные логи.
PYTHONPATH=. ./scripts/test.sh
```

Для тестов рядом с работающей db в Compose можно создать дополнительную БД killstass_test, но запускать Python-тесты надо в отдельном доверенном контейнере с backend network или на отдельной машине с тестовым PostgreSQL. Боевой порт БД ради тестов не публикуйте. Конкретный воспроизводимый вариант — [docs/06-testing.md](docs/06-testing.md).

Результаты текущей проверки и ограничения — `docs/07-verification.md`. Веб-интерфейс следует дополнительно проверить с двух реальных телефонов в домашнем Wi-Fi; это нельзя проверить на удалённом sandbox вместо ass-srv.

### 7.12 Типичные проблемы

| Симптом | Проверка / действие |
|---|---|
| bind: cannot assign requested address | На wlp2s0 нет 192.168.1.250; проверьте сеть на консоли. Не меняйте BIND_IP на 0.0.0.0 как обход. |
| permission denied /var/run/docker.sock | Перелогин после gpasswd; `id`; не делайте chmod 666 сокету. |
| docker compose: not found | Проверить реальные пакеты/cli-plugins ALT; не ставить Docker из Debian-репозитория. |
| Сертификат не доверен | Импортировать публичный CA, сверить fingerprint/время/имя; не отключать TLS. |
| origin_forbidden / CSRF | Адрес в браузере = APP_ORIGIN без завершающего /; после смены адреса перезапустить api/proxy и войти заново. |
| 502 / api unhealthy | `docker compose logs --tail=100 api db`; проверить UTF8, пароль app-роли, миграции, диск. |
| БД unhealthy после аварии | Логи PostgreSQL, место, ожидание recovery; не удалять pg_wal или файлы volume вручную. |
| 403 LAN only | Клиент вне /24, VPN, гостевой Wi-Fi или proxy меняет source IP; проверьте архитектуру сети, не расширяйте на весь интернет. |
| Телефон в LAN не открывает сайт | AP/client isolation, гостевой SSID, firewall FORWARD, адрес/DNS. SSH2026 не изменять. |
| 409 при подсчёте | Другой игрок изменил версию; обновите страницу и повторите нужное действие. Не повторяйте старую дельту новым UUID без проверки. |
| Недостаточно памяти | `docker stats`, `journalctl -k` на OOM, сократить одновременные операции/сборку; не отключать caps вслепую. |
| Медленно после старта | HDD recovery/создание индексов/обновления; проверить iostat, место; не выключать fsync ради скорости. |
| Пустая статистика | Общий матч ещё не подтверждён, спорный или фильтр скрывает дату. Гостевые видит только владелец. |
| Изменил seed, а данные прежние | Нужна новая миграция, не повторение уже применённой 002. |
| Нет писем/сброса пароля/офлайн | Эти дополнительные функции не включены, см. roadmap. |

## 9. Обновление до полной v1.1.1

В прежней поставке v1.1 использовался patch поверх v1.0. Теперь архив содержит все исходники. Не накладывайте старый patch поверх v1.1.1. `UPDATE-BASE-SHA256SUMS` сохранён как исторический файл, текущая проверка — `sha256sum -c SHA256SUMS`.

1. На ПК распаковать полный ZIP в staging, проверить суммы, сравнить локальные правки сервера.
2. На ass-srv сохранить дамп и прежние файлы; секреты и CA — отдельно защищённо. Перенести новое дерево, не удаляя `.env` и volumes.
3. От root через `su -`, из `/opt/killstass`: `docker compose config -q`, затем `./scripts/update.sh`.
4. Проверить три healthy, HTTPS с доверенным CA, `jit=off` в role/database settings и обе сессии. Состояние БД сохраняется; старые матчи остаются legacy.
5. Выполнить приёмку `docs/07-verification.md`. Подробные команды staging/backup/update/rollback и объяснение каждого исправления — `docs/10-developer-handbook.md` §6–10.

При первой установке достаточно текущего полного архива и §7. Для существующей БД переменная .env не меняет пароль роли автоматически. Не выполнять `down -v`, ручное редактирование schema_migrations и запуск старого несовместимого API.

### 9.1 Обновление справочников на ПК

Python 3.12+, без pip-зависимостей; ничего нового на ass-srv устанавливать не требуется. Начальный снимок содержит 111 записей (109 активных) и 22 шага Game Sequence. Это снимок источников на 26.10.2026, **не гарантия будущей актуальности**. Strike Force Variel и Sweep & Clear неактивны по причинам, указанным в docs/09-catalog-import.md. Русские названия — редакторские; EN сохранены отдельно. Community Maps и полные тексты правил команд не копируются.

```sh
python3 tools/catalog-import/import_catalog.py --input db/seed.json --baseline db/seed.json --dry-run
# После проверки новых сохранённых страниц и редактирования reviewed.json:
python3 tools/catalog-import/import_catalog.py --input reviewed.json --baseline db/seed.json \
  --output catalog-output --migration 005_catalog_update.sql
# Проверьте report.json, затем перенесите seed.json в db/seed.json,
# а 005_catalog_update.sql — в db/migrations/. Обновите SHA256SUMS и выполните update.sh.
```

Для деактивации исчезнувших записей добавляйте `--complete-scope wahapedia:2024:mission:approved2025` **только после полной проверки этого раздела**. Без такого флага неполная выгрузка не выключит соседние записи. Команды ручного сохранения/извлечения и источники — в docs/09-catalog-import.md. Не изменяйте уже применённые SQL. Уже начатые реальные матчи используют замороженные числовые ограничения rules_snapshot и не пересчитываются при импорте; новые получают обновлённый набор на старте.
