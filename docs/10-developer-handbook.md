# KILLSTASS 1.1.1 — руководство разработчика и оператора

Дата фиксации: 26.10.2026. Назначение: передача проекта другому разработчику, безопасное сопровождение домашней установки и сохранение результатов диагностики. Это документация существующей реализации, а не предложение переписать её.

**Главное:** v1.1.1 — полная поставка исходников. Она не содержит рабочую БД, `.env`, закрытые ключи, сессии пользователей или приватный CA. Игровой каталог остаётся снимком v1.1 на 26.10.2026; новое исследование игровых источников для этого эксплуатационного выпуска не проводилось.

## 1. Краткая карта системы

```text
Телефон / браузер в домашнем Wi-Fi
  HTTPS 192.168.1.250:443 / HTTP :80 → redirect
      │
      ▼ Docker published ports
killstass-proxy:8443 / :8080      Caddy, UID 10001
      │ backend network, HTTP
      ▼
killstass-api:8000               FastAPI, один Uvicorn worker, UID 10001
      │ psycopg pool 1–5, роль killstass_app
      ▼
killstass-db:5432                PostgreSQL 16, без host-порта
      └─ именованный db_data

Caddy CA / TLS assets → именованный caddy_data; config → caddy_config
```

Имя Compose-проекта — `killstass`; контейнеры — `killstass-db`, `killstass-api`, `killstass-proxy`. Не меняйте имя проекта при обновлении: иначе Compose может создать другие тома, и пустая база будет выглядеть как потеря данных. `backend` — внутренняя сеть; `edge` даёт прокси необходимую внешнюю связность. Имена томов следует получать через `docker volume ls`/`docker inspect`, а не угадывать.

## 3. Данные и доменные инварианты

### 3.1 Аккаунты и социальный слой

`users` хранит внутренний bigint ID, отдельный случайный публичный ID, имя и хэш пароля. Публичный ID — идентификатор для дружбы, **не секрет авторизации**. `sessions` хранит хэши токенов, `friendships` — пару пользователей, `blocks` — направленную блокировку, `challenges` — приглашения. TTL вызова по умолчанию 48 часов; это настройка `CHALLENGE_TTL_HOURS`, а не отдельный cron.

`guest_opponents` принадлежит владельцу записи. `linked_user_id` — задел для будущей привязки, не реализованный перенос истории. Гостевые матчи не создают статистику для случайного одноимённого зарегистрированного пользователя.

Удаление аккаунта — через API с повторной проверкой пароля. Общие матчи сохраняются у соперника с анонимизацией; личные гостевые записи удаляются. Старые резервные копии могут содержать прежние данные до истечения retention.

### 3.2 Общий матч

```text
принятый вызов → setup → active → awaiting_confirmation → confirmed
                                      │
                                      └─ dispute → disputed → reopen → active
```

Точные допустимые переходы проверяют `domain.py` и API. Отправитель результата не может подтвердить его сам. Подтверждение и изменение счёта выполняются в транзакции; статус `disputed` исключает матч из подтверждённой статистики. Гостевая быстрая запись — отдельный путь без подтверждения соперника, с явной отметкой этого факта.

`matches` содержит параметры и статус, `match_players` — два места игроков. `turning_point_scores` — первичные VP по источнику и повороту; `turning_point_states` — CP/заметки поворота; `operative_kills` — дельты выведенных врагов. `match_audit` хранит историю изменений. Не добавляйте параллельный «готовый итог» в `matches`: он разойдётся с первичными записями.

Каждая игровая команда проверяет участника, блокирует строку матча `FOR UPDATE`, проверяет ожидаемую `version`, меняет данные, увеличивает версию и пишет аудит. Конфликт версии возвращает 409: клиент должен получить свежий матч, а не автоматически повторять изменение с новым номером.

UUID `request_id` обеспечивает идемпотентность в рамках пользователя и содержимого команды через `operations`. Повтор с тем же payload не прибавляет VP дважды; другой payload с тем же ID — конфликт. Это не универсальная гарантия exactly-once для любого HTTP-запроса.

### 3.3 Режимы подсчёта

- `legacy`: существующие матчи v1.0. Итог — прежняя сумма VP; новые лимиты и primary bonus к ним задним числом не применяются.
- `approved2025`: новый реальный матч редакции `2024` с соответствующим пакетом правил.
- Быстрая гостевая запись: пользователь вводит уже **итоговый** счёт; повторного primary bonus нет.

Для Approved Ops Crit/Tac ограничиваются карточкой на поворот и 6 VP за направление. Выбрана одна Tac Op на игрока по архетипам его команды. У Blades of Khaine учитываются количества аспектов; отсутствие подтверждения архетипа не подменяется догадкой.

Kill grade считается по таблице порогов для исходного числа врагов 5–14 и чистой сумме дельт выведенных оперативников. Возвращение врага отражается отрицательной дельтой. Число убийств, Kill grade и Kill VP — разные величины. В конце боя сторона с большим grade получает дополнительный 1 Kill VP, при равенстве — нет.

Финальный бонус основной цели: `ceil(VP выбранного направления / 2)`. Примеры: 0→0, 1→1, 2→1, 3→2, 5→3, 6→3. Максимум всего — 21 VP. Выбор в setup предварительный; фиксация тайно в Gambit TP1, до фиксации обоих игроков нельзя перейти к дальнейшему расчёту. API не должен отдавать чужой скрытый выбор в snapshot, live-matches или audit.

На старте `rules_snapshot` замораживает источники, пороги, ограничения и выбранные карточки. Это версия входных правил, **не сохранённый итог**. Поэтому импорт новых правил не меняет результаты уже начатых матчей. Редакторское переименование справочника может изменить отображаемую подпись старой записи; для другой версии правил нужен новый стабильный code, а не скрытая замена смысла старого.

CP вводятся вручную как остаток выбранного поворота. Автоначисления, автопереноса между поворотами и полноценного контроля всех игровых действий нет. Условия на поле, измерение дистанций и исключения faction rules проверяют игроки.

### 3.4 Представления и статистика

`player_totals` вычисляет компоненты/итог; `player_results` даёт перспективу каждого игрока, допущенного в статистику. Общий подтверждённый матч даёт две перспективы, гостевой — только владельцу.

`/api/stats` выполняет SQL-агрегаты и оконные запросы: общее число, W/D/L, win rate, средние заработанные/пропущенные VP, разница, текущая/лучшая серия, разбивки по командам/миссиям/killzone и личные встречи. Выбранная Tac Op с 0 VP также участвует в соответствующей аналитике. Win rate — победы / все игры, ничья не половина победы. Серии считаются по отфильтрованной выборке; порядок при одинаковой дате стабилизирует UUID.

Временные границы фильтров и месячная группировка — Europe/Moscow, хранение — UTC. Для новых запросов не заменяйте timestamptz текстовой локальной датой. CSV экранирует потенциальные формулы в пользовательских строках; JSON предназначен для машинной обработки.

## 4. API, клиент и безопасность

Полная спецификация — `docs/03-api.md`, `docs/openapi.json`; после запуска `/api/docs` и `/api/openapi.json`.

| Область | Основные пути |
|---|---|
| Доступность | `GET /api/health` |
| Auth | `/api/auth/register`, `/login`, `/me`, `/logout` внутри `/api/auth` |
| Профиль | `/api/profile`, `/api/profile/password` |
| Связь | `/api/friends`, `/api/challenges`, `/api/notifications` и действия над ID |
| Матч | `/api/matches/{id}`, `/setup`, `/actions`, `/scores`, `/audit`, `/events` |

| Гостевой итог | `POST /api/quick-matches` |
| Справочники | `/api/catalogs`, `/api/reference/game-sequence?edition=2024` |

Авторизация — серверная сессия в `__Host-killstass`: Secure, HttpOnly, SameSite=Strict. У изменяющих запросов обязательны точный Origin, JSON и предусмотренный API CSRF-токен. Пароли Argon2id, 32 МиБ, t=2, p=1; одновременно не более двух операций в процессе. Rate limit входа/регистрации использует адрес клиента от доверенного Caddy; API не опубликован напрямую. Не включайте бездумно доверие любым X-Forwarded-For.

Типовые ответы: 401 — нет сессии; 403 — нет доступа/CSRF/Origin; 404 — нет доступного объекта; 409 — конфликт версии/операции/перехода; 422 — недопустимые поля/игровые ограничения; 429 — частые попытки; 503 — необходимые миграции не применены. Для конкретного запроса ориентируйтесь на detail и спецификацию, а не только общий список кодов.

Сервисная DB-роль без DDL; справочники доступны только SELECT, аудит — INSERT/SELECT. Это не PostgreSQL row-level security: роль приложения технически видит всю игровую БД; разграничение пользователей — ответственность API. Пароль владельца не передаётся API. Caddy/API работают без root, с read-only rootfs, cap_drop ALL и no-new-privileges; временная запись — только tmpfs, статика локальная.

SSE сообщает изменение версии, клиент перечитывает состояние; polling — запасной путь. Это не распределённый lock и не офлайн-синхронизация. Введённая форма не должна перерисовываться из-за чужого события. Проверяйте это после правок `app.js`/`ops.js`.

### Панель «Последовательность игры»

Данные находятся в `game_sequence`, а не JS-константе. Авторизованный GET использует private ETag/304; проверка сессии обязательна и для условного запроса. На устройстве кэшируется справка и checklist по матчу/редакции/версии. Отметки не синхронизируются и не блокируют начало игры.

На телефоне — нижняя панель над навигацией; на большом экране — правая рабочая область. Она не должна сбрасывать несохранённые настройки и перекрывать весь счёт. Обязательны Escape, возврат фокуса, подписи чекбоксов, цели ≥44×44, обе темы и reduced motion. Кэш справки не означает, что можно проводить матч без работающего LAN/API.

## 6. Что исправлено при реальном развёртывании

Подробный журнал — `11-deployment-changelog.md`. Ниже технические причины и точная реализация v1.1.1.

### 6.1 tmpfs: корректный YAML — не всегда корректный mount

Было `tmpfs: [/tmp:size=16m,noexec,nosuid]`. YAML воспринимает запятые как разделители трёх элементов; Docker пытается смонтировать относительный путь `noexec`. Поэтому `config -q` мог пройти, а запуск — нет.

Теперь:

```yaml
# api
    tmpfs: ["/tmp:size=16m,noexec,nosuid"]
# proxy
    tmpfs: ["/tmp:size=8m,noexec,nosuid"]
```

Опции безопасности сохранены. Для Compose-only правки нужен recreate (`docker compose up -d`), не rebuild. Новые тесты проверяют, что каждый mount — одна строка с абсолютным target.

### 6.2 Caddy: exec operation not permitted

В официальном образе бинарник может иметь file capability NET_BIND_SERVICE. С cap_drop ALL/no-new-privileges это может привести к EPERM ещё до запуска Caddy. Высокие внутренние порты 8080/8443 не требуют этой capability. В новом `proxy/Dockerfile` она снимается на этапе сборки:

```dockerfile
RUN setcap -r /usr/bin/caddy \
    && mkdir -p /data /config \
    && chown -R 10001:10001 /data /config
```

Затем `USER 10001:10001`. Не включайте privileged и не снимайте no-new-privileges как «исправление». При смене базового образа проверьте наличие setcap и capability: предложенный Dockerfile рассчитан на закреплённый Alpine Caddy. Точный getcap исходного контейнера оператор не прислал; причина EPERM — обоснованный механизм, а не полученный с хоста дамп capability.

Диагностика до изменения:

```sh
docker compose run --rm --no-deps --entrypoint /bin/sh proxy \
  -c 'id; getcap /usr/bin/caddy; ls -l /usr/bin/caddy'
```

Если EPERM сохраняется, соберите Docker inspect и kernel audit: причины host security policy тоже возможны. Не отключайте защиту ОС наугад.

### 6.3 HTTPS по IP и клиент без SNI

`curl -k` с GnuTLS давал handshake error. `openssl s_client` с явным `-servername 192.168.1.250` успешно согласовал TLS 1.3 и получил сертификат Caddy. Поэтому в **глобальный** блок Caddyfile добавлен:

```caddyfile
default_sni {$APP_HOST}
```

Он выбирает имя для ClientHello без SNI, а не создаёт доверие к CA. Это глобальная TLS-опция, не вложенная опция `servers`.[^https://caddyserver.com/docs/caddyfile/options#default-sni]

Caddyfile копируется в образ: изменение требует `docker compose build proxy` и recreate proxy. `docker compose restart proxy` не подхватывает изменённый файл с хоста.

`unable to get local issuer certificate` — отдельный вопрос доверия к частному CA. Экспортируйте **только публичный** корневой сертификат:

```sh
cd /opt/killstass
docker compose cp proxy:/data/caddy/pki/authorities/local/root.crt ./killstass-root.crt
openssl x509 -in killstass-root.crt -noout -subject -fingerprint -sha256
curl --cacert ./killstass-root.crt https://192.168.1.250/api/health
```

Проверьте fingerprint по доверенному SSH, установите CA на клиентах и откройте `https://192.168.1.250` из домашнего Wi-Fi. Для Android/iOS способ установки доверия зависит от ОС/браузера. `-k` допустим лишь для диагностики, не вместо доверия. `root.key` никому не передавайте. Не удаляйте caddy_data: это сломает прежнее доверие клиентов.

### 6.4 Медленная работа: JIT для коротких SQL-запросов

Факт с ass-srv: proxy/API потребляли мало CPU, а db — около своей квоты 1.25 CPU; свободной доступной RAM было 2.7 ГиБ, активного swap-in/out в выборке не было. `/api/health` отвечал за 0.012009 с. Это не доказывало ни нехватку памяти, ни зависание TLS; health не выполняет дорогую статистику.

В коде `/api/stats` несколько агрегирующих запросов (9) над составными представлениями. JIT может тратить на компиляцию короткого запроса больше времени, чем экономит на исполнении; решение о JIT принимается по оценке стоимости плана.[^https://www.postgresql.org/docs/16/jit-decision.html]

После отключения JIT **для роли приложения в этой базе** оператор сообщил, что решение сработало. Числового замера до/после и EXPLAIN с фактической JIT-секцией нет; точная доля затрат на компиляцию не измерена. Это подтверждённое эксплуатационное улучшение, а не нагрузочная сертификация.

Ручная команда для текущей базы:

```sh
docker compose exec -T db sh -c \
  'psql -X -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
SHOW jit;
SELECT pg_jit_available() AS jit_available;
ALTER ROLE killstass_app IN DATABASE killstass SET jit = off;
SQL
# Применение default к новым соединениям пула:
docker compose restart api
```

В v1.1.1 настройка долговременно включена в `db/migrate.sh`, **после создания роли и выдачи прав**, динамически для текущей БД:

```sql
SELECT format('ALTER ROLE killstass_app IN DATABASE %I SET jit = off', current_database()) \gexec
```

Она повторяется при первом init, update и restore; операция идемпотентна. Новая SQL-миграция 005 не нужна: на свежем init роль создаётся уже после файлов схемы, поэтому ALTER ROLE внутри такой миграции был бы ошибкой. Файлы 001–004 не изменены. Глобальный PostgreSQL `jit` и параметры других ролей/БД не меняются. Перезапуск БД не требуется; API нужно получить новые соединения.

Проверка настройки без вывода паролей:

```sh
docker compose exec -T db sh -c \
  'psql -X -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' <<'SQL'
SELECT r.rolname,d.datname,s.setconfig
FROM pg_db_role_setting s
JOIN pg_roles r ON r.oid=s.setrole
JOIN pg_database d ON d.oid=s.setdatabase
WHERE r.rolname='killstass_app' AND d.datname=current_database();
SQL
```

Ожидается `jit=off`. `SHOW jit` в соединении владельца может остаться `on` — это нормально. `SET ROLE` не имитирует загрузку login defaults; для проверки эффективного значения нужно новое прямое соединение как killstass_app. Регрессионный тест делает именно это.

Диагностический откат: `ALTER ROLE killstass_app IN DATABASE killstass RESET jit;`, затем restart api. Следующий запуск штатного migrate.sh снова установит off; для постоянного отката нужна осознанная правка эксплуатационного решения. Не меняйте пароль или таблицы ради JIT. Database-only pg_dump не следует считать полной копией cluster role settings: restore.sh повторяет мигратор и настройку явно.

### 6.5 Что НЕ подтверждено и НЕ изменено

- Нет доказанного OOM. Строка automemlimit и exit 255 сами по себе не доказывают убийство ядром. GOMEMLIMIT — мягкая цель Go runtime, не отдельный процесс, «убивающий Caddy».
- Увеличение proxy до 256 МиБ обсуждалось, но в последнем замере осталось 128 МиБ, использовано 20.76 МиБ. Поэтому релиз сохраняет 128.
- Квоты CPU, PostgreSQL buffers/WAL, парольные параметры и число API workers не повышены.
- Нет отключения fsync, checksums, autovacuum, cap_drop, no-new-privileges, TLS или fail2ban.
- Нет переписывания SQL-статистики/схемы/каталога в этом выпуске. Изменён default JIT, а не данные матчей.

## 7. Установка и безопасное обновление

### 7.1 Первая установка

Полная инструкция с обнаружением пакетов ALT, firewall и systemd — README §7. Краткий порядок:

1. Проверить сеть, SSH2026, время, свободное место и существующий firewall.
2. Root через `su -`: `apt-get update`, `apt-cache search docker`; выбрать реальные доступные ALT-пакеты engine/CLI/buildx/Compose v2, установить `apt-get install ...`. Не копировать список имён без проверки репозитория.
3. `systemctl enable --now docker`; `gpasswd -a sslaveh docker`, затем перелогин. Проверить `docker --version`, `docker compose version`, `docker run --rm hello-world`.
4. Распаковать **полный** архив в `/opt/killstass`, владелец дерева — оператор; выполнить `sha256sum -c SHA256SUMS`.
5. `./scripts/init-env.sh` создаст `.env` 0600. Не перезапускать его поверх существующего файла. Не использовать пустые пароли из `.env.example` как конфигурацию.
6. Применить правила LAN через существующую архитектуру firewall и `scripts/firewall.sh` от root. Скрипт добавляет ограничения; он не отменяет существующий DROP в другой цепочке. При строгой политике отдельно разрешить нужный трафик в действующей конфигурации. Не выполнять flush ruleset, не править Docker-таблицы/SSH наугад.
7. `docker compose config -q`, `docker compose up -d --build`, `docker compose ps`; проверить API и установить публичный CA на клиентах.
8. Зарегистрировать аккаунты, провести приёмку, настроить backup timer и off-host копию.

Если Docker Hub недоступен, используйте предварительно проверенное зеркало и `*_IMAGE` в .env либо `docker save/load` с доверенного ПК. Наличие совместимых PostgreSQL/Caddy/Python в registry.altlinux.org нужно проверить; это не взаимозаменяемые гарантированные имена. Другой базовый образ требует повторной проверки UID, setcap, entrypoint и архитектуры.

### 7.2 Обновление существующего ass-srv до 1.1.1

Если ручные исправления уже применены и сайт работает, переустановка не обязательна. Выпуск нужен для воспроизводимости будущих сборок. Сначала сравните локальные изменения: ни одна поставка не знает о неотправленных правках оператора.

**На ПК:** распакуйте ZIP в чистый staging, проверьте SHA256SUMS. В полном ZIP уже есть неизменённые файлы v1.0/v1.1; прежний patch больше не нужен. Для переноса можно собрать tar из проверенного каталога:

```sh
# ПК; в каталоге только исходники из нового ZIP
tar --exclude=.env --exclude=.git --exclude=__pycache__ --exclude=.pytest_cache \
  -czf killstass-v1.1.1-staging.tar.gz killstass/
scp -P 2026 killstass-v1.1.1-staging.tar.gz sslaveh@192.168.1.250:/home/sslaveh/
ssh -p 2026 sslaveh@192.168.1.250
```

**На сервере, в согласованное окно без несохранённых форм:**

```sh
su -
cd /opt/killstass
./scripts/backup.sh
# Сохранить исходники для diff/отката, секреты — отдельно защищённо.
tar --exclude=.env --exclude=.git --exclude=__pycache__ --exclude=.pytest_cache \
  -czf /root/killstass-pre-v1.1.1-files.tar.gz -C /opt killstass
# До извлечения проверить состав: только killstass/..., без .env, ../ и абсолютных путей.
tar -tzf /home/sslaveh/killstass-v1.1.1-staging.tar.gz
# Сравните конфиги staging с локальными правками ДО замены.
tar -xzf /home/sslaveh/killstass-v1.1.1-staging.tar.gz -C /opt
cd /opt/killstass
sha256sum -c SHA256SUMS
docker compose config -q
./scripts/update.sh
docker compose ps
docker compose logs --tail=80 db api proxy
exit
```

`update.sh` ещё раз делает backup, собирает новые образы, с v1.9 проверяет их (`scripts/smoke.sh --pre`: compose и `caddy validate` нового Caddyfile — ошибка останавливает обновление до простоя), останавливает API/proxy, пересоздаёт db с прежним volume, запускает мигратор и весь стек, затем `scripts/smoke.sh --post` (health, версия, число миграций, страница и статика через Caddy). Время сборки на HDD не равно downtime: основная остановка после build. `.env` отсутствует в архиве, поэтому существующий файл сохраняется. Не заменяйте его `.env.example`. Не делайте `down -v`, `prune --volumes` и ручной TRUNCATE.

Проверьте доверенным клиентом health, вход, список старых матчей/результаты, новую setup-панель, Game Sequence, счёт с двух сессий, аналитику и CPU db. После выпуска обновлены asset query versions до 1.1.1; при старом UI обновите вкладку. CA/аккаунты/UUID матчей должны остаться прежними.

Отдельная правка Caddyfile/Dockerfile требует `docker compose build proxy && docker compose up -d --no-deps proxy`; Compose tmpfs — recreate; ручной role JIT — restart api. Штатный update.sh делает необходимое для всей поставки.

### 7.3 Обновление из архива и откат (v1.10)

С v1.10 штатный путь — `./scripts/update.sh /root/killstass-vX.zip` (рядом `killstass-vX.zip.sha256` или `--sha256 HEX`); `--rollback` возвращает предыдущий выпуск; без аргументов — прежнее поведение над разложенными вручную файлами. Скрипт самодостаточен (не подключает `lib.sh`: обновлять его будет новая версия самого себя), требует root, держит `flock` на `/var/backups/killstass/.update.lock`.

1. **До изменений:** SHA-256 архива; распаковка во временный каталог `/var/tmp` (`unzip` → `bsdtar` → `python3 zipfile` → Python из образа `killstass-api:local` без сети и прав); `sha256sum -c --strict` по `SHA256SUMS`, список файлов равен списку сумм, нет символических ссылок, абсолютных путей, `..`, `.env`, `.env.rollback-*`, `local/`, `backups/`; версия новее установленной по `sort -V` (иначе `--force`).
2. **Сохранение:** `backup.sh` (дамп должен быть непустым), `killstass-code-<время>-<версия>.tar.gz` без `.env`/`local`/`backups` и копия `.env` (0600), хранятся 5 последних; образы `:local` → `:prev`; файл состояния `last-update` (прежняя и новая версии, пути копий, дамп).
3. **Раскладка:** удаляются файлы, которые были только в прежнем `SHA256SUMS`; остальные копируются с `--remove-destination` (новый inode — работающий shell-скрипт дочитывает старую копию); `*.sh` с shebang — 755, прочие — 644, владелец — как у `VERSION`.
4. **Развёртывание** — порядок 1.9 (build, `smoke.sh --pre`, остановка, db, мигратор, запуск, `smoke.sh --post`). Любая ошибка → `rollback()`: код из tar, `.env` (текущий сохраняется как `.env.rollback-<время>`), образы `:prev`, `docker compose up -d --wait --remove-orphans`, мигратор прежней версии, ожидание health. БД не откатывается — миграции append-only, health прежней версии считает только свои миграции; для данных печатается команда `restore.sh`.

Проверка без Docker: `tests/test_v110.py::test_update_from_archive_and_rollback` гоняет скрипт с фиктивным `docker` (успех, подмена, лишний файл, автоматический и ручной откат). Реальный прогон на ass-srv — первый пункт приёмки 1.10.

Новые скрипты оператора (v1.10) подключают `scripts/lib.sh` (644, не исполняемый): `envget`/`envset` (атомарная замена `.env` с режимом 0600 и прежним владельцем), профили `COMPOSE_PROFILES`, `allowed_nets`, `valid_cidr`, `valid_domain`, `need_root`. `domain.sh`, `cert.sh` (lego `goacme/lego:v4.29.0` в контейнере без прав, DNS-01, `local/acme`), `tailscale.sh` (профиль `tailscale`, состояние `local/tailscale`), `push.sh` (профиль `push`, `python -m api.push`), `admin.sh password`. `firewall.sh` берёт сети из `KS_ALLOW_NETS`. Каталог `local/` — данные установки, в git, архивы и образы не попадает.

## 8. Бэкапы и восстановление

`backup.sh`: pg_dump custom, сжатие уровня 3, проверка оглавления, временный файл → атомарный rename, flock от пересечения запусков, umask 077. По умолчанию `/var/backups/killstass`, последние 14 копий. Таймер — 04:30 Europe/Moscow с задержкой до 10 минут, Persistent=true.

```sh
su -
cd /opt/killstass
install -d -m 700 /var/backups/killstass
install -m 644 systemd/killstass-backup.service systemd/killstass-backup.timer /etc/systemd/system/
systemctl daemon-reload
systemctl enable --now killstass-backup.timer
systemctl start killstass-backup.service
systemctl list-timers killstass-backup.timer
journalctl -u killstass-backup.service -n 30 --no-pager
```

Факт успешного pg_restore --list проверяет структуру архива, **не заменяет пробное восстановление**. На том же HDD копия не защищает от потери диска. Перенос на ПК делайте pull по существующему SSH2026: root подготавливает файл 0600 в staging владельца sslaveh, ПК забирает `scp -P 2026 ...`, затем staging удаляется. Подробные команды — README §7.9.

Отдельно защищённо храните `.env`, версию исходников/образов, при необходимости зашифрованный caddy_data для сохранения CA. Публичный root.crt не содержит приватного ключа. Дампы содержат хэши паролей и персональные данные, не отправляйте их в issue/чат.

Для восстановления: выбрать совместимый dump и версию проекта, сделать текущую копию, затем от root:

```sh
cd /opt/killstass
./scripts/backup.sh
./scripts/restore.sh /var/backups/killstass/ИМЯ_СУЩЕСТВУЮЩЕЙ_КОПИИ.dump --yes
```

Имя заменить действительным. Скрипт проверяет архив, останавливает API/proxy, выполняет pg_restore одной транзакцией, повторяет мигратор (включая права/JIT), отзывает восстановленные сессии и запускает приложение. Всем игрокам потребуется новый вход. При ошибке сервисы остаются остановленными; не «лечите» её запуском несовместимого API. Существующий пароль app-роли мигратор не перезаписывает: при восстановлении в другой кластер синхронизируйте `.env` и роль интерактивной `\password`, не аргументом shell.

### 8.1 Обратная связь и страница администратора (v1.5, v1.9)

С v1.9 отзывы читаются на странице `#admin` (новые/все, «Обработано»/«Вернуть»); там же сводка (версия, миграции, счётчики, размер БД, последняя загрузка справочника) и поиск пользователей. `scripts/feedback.sh` удалён. Доступ выдаёт владелец БД:

```sh
./scripts/admin.sh grant LOGIN     # дать доступ к #admin
./scripts/admin.sh revoke LOGIN    # забрать
```

Роль приложения не может поменять `users.is_admin` (мигратор оставляет ей запись только в колонки регистрации, имени и пароля). Сообщения хранятся только в БД сервера и входят в обычный backup. Подробно — `15-utilities.md`, `19-v1.9.md`.

### 8.2 Справочник команд (v1.7)

Данные (тексты GW из общественных репозиториев) не входят в поставку; загружает администратор. Пишет владелец БД, роль приложения только читает. Справочник входит в обычный backup; после восстановления повторный импорт не нужен. Подробно — `17-teams-and-design.md`.

### 8.3 Справочник правил и его обновление (v1.11)

Пакеты до и после каждого запуска — в `/var/backups/killstass/reference/<UTC-время>` (5 применённых и последний неудачный), журнал — таблица `reference_updates` и раздел «Справочник правил» в `#admin`. Загрузка, обновление поискового индекса и запись журнала — одна транзакция владельца БД; роль приложения только читает. Скачивание — во временных контейнерах образа api, само приложение в интернет не ходит. warhammer-oracle читается как данные (TS-литералы разбирает `api/rulesdata.py`), его код не запускается. Подробно — `21-v1.11.md`.

### 8.4 Основные правила и готовый террейн (v1.12)

Основные правила (`#core`) входят в поставку: `api/data/core-rules.json` собирается разработчиком из `tools/core-rules/src/*.md` (`python3 tools/core-rules/build.py`, проверка — `--check`, её же выполняет `tests/test_v112.py`), на сервере ничего загружать не нужно. Правка текста (например, после нового обновления правил GW): с v1.13 изменения вносятся прямо в текст исходника — без пометок и без страниц PDF (страница показывает только действующие правила); пересобрать JSON, проверить страницу `#core` и выпустить версию — `version` документа и его ETag сменятся сами. Официальные документы — на warhammer-community.com (раздел загрузок Kill Team; список отдаёт `POST https://www.warhammer-community.com/api/search/downloads/` с телом `{"index":"downloads_v2","searchTerm":"","gameSystem":"kill-team","language":"english"}`): «Core Rules: Update Log» — исправления основных правил, «Universal Equipment» — профили гранат калькулятора.

### 8.5 Сдача, локальные игроки, число оперативников, подсказки (v1.13)

Сданный матч хранит `matches.conceded_slot`; счёт 10:0 считает только представление `player_totals` — менять запросы статистики, рейтингов, сезонов и турниров не нужно. Локальные игроки — таблица `local_players` (общая для клуба, уникальна по `ks_fold(name)`); администратор удаляет записи в `#admin` («Локальные игроки»), матчи остаются с именем и выходят из рейтинга клуба. Отдельной команды оператора для них нет: при необходимости — `DELETE FROM local_players WHERE id=…` от владельца БД (ссылки в `match_players` обнулятся сами).

Число оперативников по составу команды вычисляется из уже загруженных данных (`team_data.data->'selection'` и `roster_schema`) при первом запросе каждой версии импорта и кешируется в процессе API (`api/teams._SIZES`); после `import-teams.sh`/`update-reference.sh` пересчитывается само. Подсказки — `tools/core-rules/src/terms.md`: новый термин — строка с id, видом, названиями, ссылкой на абзац основных правил и синонимами; `build.py` проверит, что ссылка указывает на существующий текст, а синонимы компилируются; затем `--check` и `#core`/датакарты в браузере.

### 8.6 Группы меню, карточка оперативника, снаряжение, CP и ploys, журнал ошибок (v1.14)

Новый раздел интерфейса добавляется строкой в `web/sections.js` (`SECTIONS` и `items` нужной группы) и маршрутом в `ROUTES` (`web/app.js`); модульный тест `unit.test.mjs` проверит группу, маршрут, иконку и переводы. Число для плитки — поле в `api/navsummary.py` (только счётчики, без названий и имён) и строка в `groupPage`.

Правила оперативника собирает сервер (`api/tracker.py roster_build`) из уже загруженной схемы ростера: миграции и повторного импорта не нужно. Снаряжение — тоже из схем (`api/equipment.py schema_items`); у команды без снаряжения в схеме — снаряжение команды из справочника (`equipment` датакарт), универсальное — из схемы любой команды (кеш процесса API по хэшу схемы). Выбор игрока хранится серверной копией в `match_players.equipment`, поэтому смена справочника не меняет сыгранные матчи; до старта чужой выбор не отдаётся (`redact`).

CP начисляются записью в `match_cp_grants` (ключ — матч и поворотный момент) и изменением `turning_point_states.cp`; ploys — строкой `match_ploys` и тем же `cp`. Обе операции идут через `core.operation` (идемпотентность по `request_id`) и аудит, «Отменить» — через `tracker.revert` → `command.revert`. В 2021 снаряжения и начисления нет (проверки `edition` в `api/equipment.py` и `api/command.py`), ploys — в обеих редакциях.

Журнал ошибок браузера наполняется сам; хранение — 30 дней и не больше `ROW_CAP` строк (`api/clienterrors.py`), очистка — кнопкой в `#admin` или `DELETE FROM client_errors` от владельца БД. Ошибки там — повод открыть страницу в браузере и посмотреть консоль; данные форм и параметры адресов в журнал не попадают.

## 9. Диагностика без догадок

### Минимальный безопасный снимок

```sh
cd /opt/killstass
uptime
free -h
vmstat 1 5
docker stats --no-stream
docker compose ps
df -h
docker compose logs --tail=100 api db proxy
curl --cacert ./killstass-root.crt -sS -o /dev/null \
  --connect-timeout 3 --max-time 15 \
  -w 'HTTP=%{http_code} TCP=%{time_connect}s TLS=%{time_appconnect}s FIRST_BYTE=%{time_starttransfer}s TOTAL=%{time_total}s\n' \
  https://192.168.1.250/api/health
```

Перед публикацией логов удалить персональные данные, cookies, токены, DSN и секреты. `docker compose config` без `-q` и `docker inspect` целиком могут раскрыть environment; не прикладывайте их без очистки.

| Симптом | Проверить прежде всего |
|---|---|
| invalid mount path: noexec | цитирование scalar tmpfs, не удалять noexec |
| exec caddy EPERM | file capability, Dockerfile, cap/security options, kernel audit |
| handshake error до HTTP | SNI/IP/сертификат/часы, а не auth и не SQL |
| issuer certificate error | доверие публичному локальному CA и fingerprint |
| 401/403 после входа | одинаковый HTTPS origin, Secure cookie, CSRF/Origin, часы, не заходить по другому имени |
| 409 при счёте | версия матча / request_id, перечитать состояние и согласовать правку |
| health быстрый, аналитика медленная | DB CPU, pg_stat_activity, JIT новых app-соединений, план конкретного SELECT |
| контейнер рестартует | inspect OOMKilled/ExitCode/Error/RestartCount и kernel logs |
| пустая история после обновления | имя Compose/volume/БД и аккаунт; не создавать новую БД поверх старого тома |
| CA неожиданно сменился | какой caddy_data примонтирован; не доверять новому ключу до проверки |

Проверка остановки, без вывода env:

```sh
docker inspect --format 'OOM={{.State.OOMKilled}} Exit={{.State.ExitCode}} Error={{.State.Error}} Restarts={{.RestartCount}} Limit={{.HostConfig.Memory}}' killstass-proxy
# root:
journalctl -k --since '30 minutes ago' | grep -Ei 'oom|out of memory|killed process|denied' || true
```

Свободные 122 МиБ при available 2.7 ГиБ — не основание добавлять swap. В Docker 100% CPU примерно соответствует одному CPU; 125% у db при cpus=1.25 может означать достижение квоты, хотя общий CPU хоста свободен. Первый vmstat-сэмпл обычно средний с загрузки, не текущая секунда.

При повторной SQL-проблеме сначала изучить `pg_stat_activity` (владелец через psql), длительность/ожидания и конкретный запрос. `EXPLAIN (ANALYZE, BUFFERS, SETTINGS)` действительно исполняет запрос: используйте копию данных и SELECT, не пишущие команды на production. Сравните одинаковые параметры/кэш/число матчей при jit on/off. Не выдавайте рост mem_limit за исправление неоптимального плана.

### Обязательный review изменений

1. **Схема:** только следующий SQL-файл. Не переписывать 001–004 и не править schema_migrations вручную. Проверить upgrade с существующими матчами и fresh init.
2. **Права:** новый объект не должен случайно дать DDL/изменение каталога app-роли; мигратор повторно выставляет grants.
3. **Итоги:** сравнить player_results старой БД до/после, границы ceil/caps, secret choices, dispute/reopen, двойной request_id.
4. **Клиент:** несохранённая форма при SSE/panel, два аккаунта, мобильная навигация и длинные RU-строки, светлая/тёмная тема.
5. **Конфигурация:** `config -q` + разбор mount-строк + реальный Compose startup. Проверить non-root/cap_drop/read-only, а не только caddy validate.
6. **Релиз:** номер только в `VERSION` (с v1.9 тест сверяет `package.json`, `docs/openapi.json`, заголовки README/UPDATE-INFO); OpenAPI, docs и SHA256SUMS согласованы; `npm run lint` и `npm run e2e` зелёные; новых secrets/dumps/cache/HTML источников нет.
7. **Эксплуатация:** backup/restore в отдельном экземпляре, здоровые сервисы после reboot, доверие CA на клиентах, CPU/latency на ass-srv.

Health API проверяет доступ к БД и наличие 001–004, но не доказывает скорость статистики и правильность всех каталогов. Healthcheck db с историческим порогом count>=2 — только readiness базы; schema readiness приложения проверяет API. Для будущей 005 отдельно обновите требования readiness и тесты, если новая схема обязательна API.

### Границы подтверждения v1.1.1

Точные результаты повторных тестов выпуска — `07-verification.md`. В текущем окружении нет Docker daemon: полный образный запуск не сертифицирован.
