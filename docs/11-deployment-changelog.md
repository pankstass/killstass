## 2. События и уровень подтверждения

### D-01. Неверное разбиение tmpfs

**Получено от оператора:** запуск Docker остановился с `invalid mount path: 'noexec' mount path must be absolute`. grep показал `tmpfs: [/tmp:size=16m,noexec,nosuid]` и аналогичную строку 8m.

**Причина:** flow sequence YAML разделила одно описание mount на три элемента. Это подтверждается самой конфигурацией и ошибкой Docker.

**Правка:** строка целиком в кавычках: `tmpfs: ["/tmp:size=16m,noexec,nosuid"]`, аналогично 8m. Ограничения noexec/nosuid не удалены. Включено в v1.1.1.

**Вывод для QA:** успешный compose config -q в предыдущем отчёте не доказывал корректность семантики mount. Этот пробел не скрывается; добавлен регрессионный тест. На следующем целевом запуске нужен фактический recreate контейнеров.

### D-02. Caddy не исполнялся

**Получено:** повторяющийся `exec /usr/bin/caddy: operation not permitted`.

**Предложенный механизм:** file capability NET_BIND_SERVICE у бинарника официального образа в сочетании с урезанными capabilities контейнера. Вывод getcap с ass-srv не получен, поэтому это не объявляется независимо доказанной единственной причиной.

**Правка поставки:** снять file capability через `setcap -r` на этапе build; сохранить non-root UID 10001, cap_drop ALL, no-new-privileges, внутренние 8080/8443. Не нужны privileged и низкие порты внутри контейнера. Позднее оператор получил работающий TLS и healthy proxy — успешный запуск процесса подтверждён, но полная рабочая конфигурация хоста не снималась.

### D-03. Обсуждение automemlimit / OOM

Предположение, что automemlimit или exit 255 доказывает нехватку памяти, **не подтверждено**. Не получены OOMKilled=true, kernel OOM-запись или воспроизводимый пик RSS. Soft GOMEMLIMIT не равен отдельной утилите завершения процесса.

Увеличение proxy 128→256 МиБ не включено в релиз. Последний присланный Docker stats показывает **20.76 МиБ из 128 МиБ**. Общий бюджет остаётся 1152 МиБ, лимиты CPU также без изменений.

### D-04. TLS по IP

**Получено:** `curl -k` (GnuTLS) завершился handshake error. Затем `openssl s_client` с явным `-servername 192.168.1.250` согласовал TLSv1.3 / TLS_AES_128_GCM_SHA256, предъявлен сертификат Caddy Local Authority. Вывод содержал verify error 20 (не установлен доверенный issuer).

**Правка:** `default_sni {$APP_HOST}` в глобальном блоке Caddyfile; пересборка proxy, так как файл COPY в образе. Отдельно — установка публичного CA на клиентах. Прямого сравнительного вывода openssl без SNI не получено; механизм и документированная опция согласуются с наблюдением.

**Позднее подтверждение:** запрос обычного HTTPS health вернул HTTP 200; оператор смог открыть сайт, зарегистрировать два аккаунта с двух устройств и записать матч. Доверие CA на каждом типе ОС отдельно не сертифицировано.

### D-05. Медленная авторизация/страницы после начала работы

**Получено от оператора:** после регистрации и матча сайт отвечал медленно; вход требовал повторных попыток. Минимальный снимок:

| Метрика | Значение |
|---|---:|
| Load average | 0.32 / 1.23 / 0.83 |
| RAM total / used / available | 3.7 / 1.0 / 2.7 ГиБ |
| buff/cache / free | 2.9 ГиБ / 122 МиБ |
| Swap used | 780 КиБ; vmstat si/so=0 |
| Текущие vmstat-сэмплы | idle 66–68%, wa 0–1% |
| proxy CPU / память | 0.00% / 20.76 МиБ из 128 |
| api CPU / память | 0.44% / 48.2 МиБ из 384 |
| db CPU / память | 125.11% / 288.5 МиБ из 640 |
| Статусы | все три healthy |
| Диск / использовано | 454 ГБ / 4.1 ГБ, около 1% |
| health HTTP | 200 |
| TCP / TLS | 0.000361 / 0.004895 с |
| first byte / total | 0.011644 / 0.012009 с |

Это один снимок, не длительное наблюдение. Available, а не только free, важен для вывода о памяти. По нему нет оснований считать RAM/HDD заполненными; быстрый health не характеризует сложную аналитику. db CPU около квоты 1.25 CPU стал основанием исследовать запросы.

**Решение:** `ALTER ROLE killstass_app IN DATABASE killstass SET jit = off;` и restart api для новых DB-соединений. SQL-агрегаты по представлениям способны получать дорогие оценки плана, провоцирующие JIT overhead. Измерений EXPLAIN/JIT time нет.

**Подтверждение:** оператор явно сообщил «Решение сработало». Это подтверждает улучшение поведения, но не конкретный коэффициент ускорения. Числовые latency/CPU после правки не присланы и не выдумываются.

**Фиксация в v1.1.1:** идемпотентный ALTER ROLE ... IN DATABASE через format(current_database()) в конце db/migrate.sh после создания роли. Fresh init/update/restore получают одинаковую настройку. Старые SQL-миграции и данные не изменены, серверный jit глобально не отключён.

## 4. Приёмка выпуска на целевом сервере

1. До обновления: backup, копия исходников, сравнение локальных изменений, согласованная пауза игры.
2. Полный архив + SHA256SUMS → сохранить .env и volumes → scripts/update.sh.
3. Все три healthy, логи без повторного EPERM/mount error; CA прежний, HTTPS health с --cacert успешен.
4. pg_db_role_setting содержит jit=off для killstass_app / текущей БД. API после мигратора перезапущен.
5. Два устройства: вход, старые матчи/итоги, setup и sequence без сброса формы, общий счёт, finish/confirm, статистика.
6. Записать новый одинаковый замер health/stats, docker stats, vmstat. Нет обещанного времени ответа без реального измерения.
7. После этого backup, проверка timer и восстановление в отдельном экземпляре. Перезагрузка хоста — отдельная проверка возврата systemd/Docker/firewall.

Готовые команды и процедуры отката находятся в docs/10-developer-handbook.md. Повторная установка не нужна, если все ручные исправления уже действуют; главная цель архива — их воспроизводимое сохранение.

### D-07. Тестовый образ без файлов, которые читают тесты

С 1.9 тесты читают `scripts/`, `systemd/`, `README.md`, `UPDATE-INFO.md`, `package.json`, `docs/openapi.json`, а `tests/Dockerfile` копировал только `api/`, `db/`, `tests/` и Compose/proxy — в контейнере такие тесты падали. ### D-08. Обновление из ZIP и откат

`update.sh ZIP` проверяет архив до каких-либо изменений, сохраняет код, `.env` и образы и при ошибке откатывается сам; `update.sh --rollback` — вручную. Проверено фиктивным `docker` в `tests/test_v110.py` и отдельным стендом: успех, `--rollback`, автоматический откат после сбоя сборки, проверок до и после запуска и мигратора, неверная или отсутствующая сумма, подменённый и лишний файл, версия та же или старее, `--force`, хранение 5 выпусков, режим без аргументов. Скрипты оператора, правящие `.env` от root, сохраняют его владельца и режим 0600.

### D-09. Новые необязательные сервисы

`pushworker` (профиль `push`) и `tailscale` (профиль `tailscale`) не запускаются, пока их не включат `push.sh`/`tailscale.sh`; lego запускается разово (`cert.sh`, таймер `killstass-cert.timer`). Proxy монтирует `local/acme/certificates` только для чтения (Docker создаст пустой каталог, если его нет). Проверено: `docker compose config` (Compose v2.40.3) с профилями и без, `caddy validate` (Caddy 2.10.0) для режимов `internal`/`files` и с несколькими сетями, флаги и коды DNS-провайдеров — по бинарнику lego v4.29.0, `firewall.sh` — с фиктивными `iptables`/`nft`. Не проверено: реальный выпуск сертификата, вход Tailscale и маршрут, доставка push, правила firewall на ядре ass-srv.

### D-10. Tailscale: поток от сервера координации замирает через порт 80

ass-srv, 2026-11-03, `tailscale/tailscale:v1.104.4`. Вход прошёл (`RegisterReq: … machineAuthorized=true`), сервер получил первую карту сети, соединение с DERP (Хельсинки) установлено. После этого ни одного ответа: `control: map response long-poll timed out!` каждые 2 минуты, `PollNetMap: Post "https://controlplane.tailscale.com/machine/map": context canceled`, в `tailscale status` свой узел `offline`, предупреждение «Tailscale hasn't received a network map from the coordination server». При этом с того же сервера `curl https://controlplane.tailscale.com/derpmap/default` (15 КБ по HTTPS) отвечает за 0,3 с; перезапусков и OOM у контейнера нет. Провайдер — с CGNAT (WAN-адрес роутера по NAT-PMP — из 100.64.0.0/10, внешний по STUN — другой), `MappingVariesByDestIP: false`.

Причина (по коду клиента `control/controlhttp`): Noise-соединение с координатором по умолчанию идёт по HTTP на порт 80, 443 пробуется только если 80 не ответил; автоматический переход на 443 срабатывает, только если предыдущий дозвон был меньше 2 минут назад, а таймаут long-poll — ровно 2 минуты. Вероятно, порт 80 у провайдера идёт через прозрачный прокси, который пропускает Upgrade и затем держит поток (тот же случай — tailscale/tailscale#13597). Исправление: `TS_FORCE_NOISE_443: 'true'` в сервисе `tailscale` (в 1.10.0 на сервере — через `docker-compose.override.yml`, `update.sh` его не трогает). Подтверждено на ass-srv 2026-11-04: после перезапуска контейнера с override узел больше не уходит в offline. В следующем выпуске переменная уже в `docker-compose.yml`, override после обновления можно удалить.

### D-12. Обновление справочника: новые файлы на сервере

Блокировка `reference/.lock` не даёт запустить два обновления; плановый бэкап (`killstass-backup.timer`) скрипт дожидается до 15 минут. Скачивание — `docker run` образа `killstass-api:local` с `--network bridge`, `--read-only`, `--cap-drop ALL`, как у `import-teams.sh`; нужен доступ к `api.github.com` и `raw.githubusercontent.com`. Проверено с фиктивным `docker` (`tests/test_v111.py` и отдельный стенд): обновление, «без изменений», `--check`, откат и повторный откат, сбои скачивания и проверки (ничего не загружается, ошибка в журнале), `--status`, ротация. Обновление — `scripts/update.sh` с архивом 1.14.0, откат — `--rollback`: 1.13.0 не читает новый столбец и таблицы, CP, начисленные и потраченные в 1.14, остаются в счёте поворотных моментов. Браузерные тесты в Docker: `E2E_BROWSERS="chromium firefox webkit" ./scripts/e2e-docker.sh` — тот же образ Playwright, по умолчанию только Chromium.
